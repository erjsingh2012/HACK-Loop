Component Health vs. Funnel Failure

USE sees the component. Funnel Analysis sees the journey.

Traditional infrastructure monitoring asks whether individual resources are healthy: CPU, memory, disk I/O, queues, and errors. But application failures can leave almost no footprint at the infrastructure layer. A silent API hang, an unresolved promise, a stalled third-party SDK, or a failure at a geographic edge can leave CPU at 2% while user conversion approaches 0%.

The key idea is event accounting: define observable boundaries in the journey and reconcile what enters each boundary with what leaves it. The governing equation:

Input Events = Output Events + ΔBuffer + Sinks
Output — happy-path completion ΔBuffer — queued, in-flight, or awaiting retry Sinks — failure, error, expiration, cancellation, or discard

A conventional failure takes a path. A catch block fires. A timeout resolves. An error counter increments. But an operation that never settles bypasses every one of those mechanisms — it neither succeeds nor fails. A server can remain almost completely idle while thousands of user operations are stuck waiting for something that will never happen.

An unexplained remainder is itself a signal: either the system lost the event, or the instrumentation failed to account for it.

Diagnostic Readiness

Dimensioned Baselines — What does healthy look like?

Establish conversion and resolution baselines across meaningful dimensions: OS, runtime, hardware tier, region, network path, app version, and temporal cycles. Healthy cannot be defined during an outage — it must be established before one.

USE + Funnel Matrix — Where is the pressure or loss?

Pair node-level resource signals with path-level event accounting. Track Utilization, Saturation, and Errors alongside event ingress, transitions, terminal outcomes, queues, retries, and unresolved operations. USE identifies pressure at the component; Funnel Analysis identifies loss across the journey.

Sampling Normalization — Can we trust the numbers?

Use aggressive sampling for high-volume healthy paths while retaining failures at a higher sampling rate, ideally 100% for critical failure signals. For unbiased probabilistic sampling, estimated volume can be recovered through inverse-probability weighting (1 / sample_rate). At a 5% sampling rate, an observed count can be scaled by 20.

Dynamic Instrumentation — Can we see the dark path?

Use runtime feature flags, targeted tracing, and dynamic instrumentation such as eBPF/BCC-style hooks to expose otherwise invisible execution paths without requiring a full service redeployment. If a critical path cannot be observed, diagnosis becomes inference rather than evidence.

Anomaly detection should operate on two planes: absolute (a metric crossed a defined threshold) and relative (a metric diverged materially from its historical behavior, even without crossing a hard threshold). A 38% resolution rate might look stable in isolation. Compare it with last Tuesday's 97%, and the anomaly becomes obvious.

Pre-Incident Architecture Mapping

Layering Funnel Analysis onto the C4 Model provides a structured way to map diagnostic coverage before an outage occurs.

LevelFocus
1 — System Context Conversion and failure drop-offs across external boundaries: third-party vendor APIs, payment processors, social authentication flows, and cross-border gateways.
2 — Containers Transitions between runtime environments, microservices, and databases using cross-boundary tracer strings such as session_start → auth_ok → ad_req, together with latency measurements (ΔT).
3 — Components Internal execution flows and drop-offs across application modules such as AdLoadManager → SDK Adapter → Retry Handler. Narrows the failure domain to the specific component boundary.
4 — Code Lowest-level execution points around async operations: Promise.race() wrappers, explicit timeouts, fallback metrics, thread dumps, and targeted diagnostic hooks.

The Three W's

At each boundary, Funnel Analysis answers the same three questions:

Where?
Location
Which boundary, service, dependency, or code path stopped accounting for events?
Which?
Dimension
Which geography, language, OS, app version, network condition, or hardware tier?
When?
Temporal anchor
When was the funnel last balanced, providing the anchor for the investigation?
Count what entered. Count what exited. Investigate the difference.

If those questions cannot be answered from available telemetry, the first problem to solve is not the application code. It is the instrumentation gap.

What H.A.C.K. Prevents

Incident anti-patterns share a common structure: action is taken before the failure domain has been established. H.A.C.K. makes these patterns explicit so they can be recognized — and interrupted.

🔦
The Streetlight Anti-Method
"I only search where my existing tools already look."

Searching familiar logs and dashboards instead of investigating the unobserved path. When monitoring covers only the happy path, engineers naturally look there first — even when the failure has already disappeared into a dark path.

Why it happens
Under pressure, engineers reach for familiar tools. When time is short and stakes are high, the instinct is to search where answers have been found before, rather than where the evidence says the problem may actually be.
How to address it
Start with 5–10 minutes of surface checks. If no smoking gun emerges, instrument the dark path instead. Isolate the specific journey, count what entered versus what resolved, and let the unexplained gap identify the boundary worth investigating.
👉
The Cross-Boundary Deflection Anti-Method
"It's probably a third-party vendor or platform problem."

Escalating a cross-boundary failure based on intuition rather than evidence. Without measurable evidence at the boundary, a vendor has no reason to act — and no reliable way to reproduce the failure.

Why it happens
Cross-boundary failures are genuinely harder to prove. Without shared telemetry across both sides, assuming the problem lives somewhere else can feel reasonable. Suspicion is easier to communicate than evidence is to gather.
How to address it
Isolate the failing journey before escalating. Measure what crossed the boundary, what returned, and what remained unaccounted for. Evidence transforms "your system is broken" into a reproducible signal the other side can investigate.
🍺
The Drunk Man Anti-Method
"I tweaked a config and the symptom stopped, so we're done."

Changing configurations or deploying patches until the metric recovers — without establishing why it recovered.

Why it happens
Correlation feels like causation under incident pressure. When a change coincides with recovery, the brain naturally connects the two. Once the metric turns green, the team is often too relieved to challenge the explanation.
How to address it
Before declaring resolution, establish the mechanism. Ask: what changed in the execution path, and why should that change produce this outcome? If the explanation does not hold against the evidence, the symptom may have been masked rather than resolved.
🚦
The Traffic Light Anti-Method
"Everything is green on the dashboard, so we're healthy."

Treating infrastructure health as a proxy for application health. A server can report healthy CPU, memory, disk, and error metrics while users are completely blocked. A client-side SDK can hang indefinitely without creating meaningful server-side pressure.

Why it happens
Dashboards are optimized around the signals we already know how to measure. Green infrastructure metrics create a false sense of completeness when the user journey itself is not being measured.
How to address it
Treat infrastructure health as necessary, not sufficient. Pair component-level health with journey-level Funnel Analysis. If the infrastructure is green but conversion is falling, follow the event path rather than the dashboard color.

Accelerating H.A.C.K. with AI (C.H.A.I.)

LLMs can accelerate specific points in the H.A.C.K. loop — not by acting as autonomous investigators, but by processing structured evidence and reducing time between observation, hypothesis, and intervention.

[C] Context
Trap Authoring
Given an architecture diagram, call graph, or execution trace, an LLM can identify instrumentation gaps and propose diagnostic interventions — Promise.race() wrappers, targeted logging, or eBPF-style trace hooks. Candidate traps for validation, not production changes.
[H] Health
Baseline Parsing
Given funnel metrics, log excerpts, or query outputs, an LLM can surface cohort-level patterns and identify divergence across dimensions that aggregate dashboards may hide.
[A] Anomaly
Hypothesis Isolation
Given trace dumps, drop-off events, deployment diffs, and dependency signals, an LLM can organize and rank competing hypotheses by their consistency with the available evidence — reducing the hypothesis space before expensive diagnostic work begins.
[I] Intelligence
Knowledge Synthesis
Given incident timelines, diagnostic findings, and resolution artifacts, an LLM can synthesize the evidence into postmortems, regression-test scaffolding, investigation checklists, and runbook updates.
AI can accelerate the loop, but evidence still closes it.

Case Study

P0 — Revenue Critical Signal: Ad Funnel Collapse
H Health

Gameplay engagement remained entirely normal, but interstitial ad impressions plummeted on iOS runtimes without a release rollout.

A Anomaly

Discrepancy analysis between ad_request events and terminal ad_load resolutions exposed a pool of unresolved operations:

Requests (ad_request = success)
100%
Resolved (ad_load success/fail)
62%
Unaccounted (hanging promises)
38%
↑ Silent promise hangs — never resolved, never rejected
SELECT
    counter_date,
    event_category AS ad_type,
    COUNT(DISTINCT session_id) AS total_affected_sessions,
    SUM(CASE WHEN event_name = 'ad_request' AND event_status = 'success' THEN 1 ELSE 0 END) -
    SUM(CASE WHEN event_name = 'ad_load'   AND event_status IN ('success','fail') THEN 1 ELSE 0 END)
    AS net_hanging_promises
FROM telemetry.event_counts
WHERE app_id = 1000123 AND counter_date >= '2026-02-20'
GROUP BY counter_date, ad_type
HAVING net_hanging_promises > 0;
C Candidate Fix

A third-party social SDK was failing to settle promises under specific iOS conditions. Standard catch blocks never fired — the operations simply hung indefinitely. The team deployed a 20-second Promise.race() cutoff trap:

const adLoadWithTimeout = Promise.race([
    sdk.loadAd(adUnitId),
    new Promise((_, reject) =>
        setTimeout(
            () => reject(new Error('PLATFORM_SDK_TIMEOUT | Platform: iOS')),
            20000
        )
    )
]);
K Knowledge

Timeout telemetry provided strong boundary evidence for vendor escalation, leading to vendor-side remediation and permanent sanity-check automation.

Resolution: Third-party iOS SDK failed to settle promises → Vendor remediated; production fully restored.
Prevention: Unresolved async operations lacked hard cutoffs → Automated 24-hour sanity check suite scheduled.

· · ·

The postmortem is what makes the next incident shorter — the record of what failed, where it failed, how evidence exposed it, why the intervention worked, and how the system can automatically catch or prevent that failure class next time.

The H.A.C.K. Loop is not a checklist.

It is a habit of thought: measure, investigate, validate, learn. Repeat.
