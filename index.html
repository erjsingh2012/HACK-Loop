The H.A.C.K. Loop

An Evidence-First Framework for Diagnosing Application Anomalies, Issues, and Outages

USE + Funnel Analysis + H.A.C.K. — Building on Brendan Gregg's USE Method with journey-level application observability.

When production breaks, the instinct is to guess, patch, and see if the bleeding stops. The H.A.C.K. Loop builds on Brendan Gregg's evidence-first USE Method, adding Funnel Analysis to expose journey-level failures that infrastructure metrics can miss.

Here, Funnel Analysis means event-flow accounting across an application journey — not simply product or marketing conversion analysis.

The Framework

H.A.C.K. is an evidence-driven investigation loop for diagnosing application anomalies — especially those invisible to infrastructure-level monitoring. It applies the evidence-first discipline of Brendan Gregg's USE Method to the application journey layer: not just is this component healthy? but did this event make it through?

Anti-patterns jump directly to a candidate fix based on intuition and stop once symptoms clear. H.A.C.K. enforces an evidence-driven sequence — every time.

Application Event Accounting

At any defined application boundary — an SDK call, an authentication flow, an ad request — every operation that enters should eventually exit through one of three paths: a successful completion, an explicit failure or terminal state, or a bounded in-flight operation awaiting resolution.

$$\text{Inputs} = \text{Outputs} + \Delta\text{Buffer} + \text{Sinks}$$
Inputs — Total operations entering the defined application boundary. Outputs — Successfully resolved happy-path completions. ΔBuffer — Bounded in-flight operations: queued, retried, or deferred. Sinks — Explicitly handled terminal states: failures, errors, timeouts, cancellations.

When this equation doesn't balance — when operations enter and never resolve in any direction — the remainder is not noise to discard. It is a signal.

An unexplained remainder is itself a signal.

A conventional failure takes a path. A catch block fires. A timeout resolves. An error counter increments. But an operation that never settles bypasses every one of those mechanisms — it neither succeeds nor fails. Infrastructure can remain completely idle and error-free while thousands of user operations are silently stuck. The system looks healthy because the component is healthy. The journey is not.

Case Study: P0 Ad Funnel Collapse

The following investigation applies the H.A.C.K. Loop to a real revenue-critical incident. It illustrates concretely why component-level monitoring was insufficient, and how event accounting located the failure domain.

INC-2026-AD-REQ-DOWN  ·  P0 Revenue Critical  ·  iOS Ad Funnel Collapse

The Symptom

Gameplay engagement remained entirely normal. Infrastructure metrics stayed within nominal thresholds. No binary release had gone out. Yet interstitial ad impressions on iOS collapsed.

This is a textbook traffic-light failure: everything visible to infrastructure monitoring remained green while an application journey silently failed. Without journey-level instrumentation, there was no starting point for investigation.

H — Health

The expected funnel was straightforward. In a healthy system, every successful ad_request should eventually produce either a success or failure at ad_load. Every initiated operation should reach a terminal state.

ad_request (success)  →  ad_load (success | fail)

The baseline expectation was near-complete resolution — effectively 100% of requests reaching a terminal outcome. Healthy cannot be defined during an outage. It must be established before one.

A — Anomaly

Discrepancy analysis between ad_request events and terminal ad_load resolutions exposed a large pool of unresolved operations:

REQUESTS (ad_request = success) ████████████████ 100% RESOLVED (ad_load success/fail) ██████████ 62% UNACCOUNTED (hanging promises) ██████ 38% ↑ Silent promise hangs
The problem was not an increase in explicit errors. It was missing terminal states.

38% of observed requests had no corresponding terminal event within the accounting window. The operations were initiated but never triggered a success or failure callback. Server and client CPU remained within nominal thresholds throughout.

The query below was not looking for errors. It was looking for requests that entered the system without reaching a terminal state — the accounting gap itself:

SELECT
    counter_date,
    event_category AS ad_type,
    COUNT(DISTINCT session_id) AS total_affected_sessions,
    SUM(CASE WHEN event_name = 'ad_request' AND event_status = 'success' THEN 1 ELSE 0 END) -
    SUM(CASE WHEN event_name = 'ad_load'   AND event_status IN ('success','fail') THEN 1 ELSE 0 END)
    AS net_hanging_promises
FROM telemetry.event_counts
WHERE app_id = 1000123 AND counter_date >= '2026-02-20'
GROUP BY counter_date, ad_type
HAVING net_hanging_promises > 0;
C — Candidate Fix

Isolation pointed to a third-party social SDK failing to settle promises under specific iOS runtime conditions. Standard catch blocks never fired — the operations simply hung indefinitely.

A 20-second Promise.race() cutoff was injected at the interop boundary to test the hypothesis. The intent was diagnostic: if operations were truly hanging, the timeout would convert invisible hangs into explicit, observable rejections.

silent hang → bounded timeout → explicit failure → observable telemetry
const adLoadWithTimeout = Promise.race([
    sdk.loadAd(adUnitId),
    new Promise((_, reject) =>
        setTimeout(
            () => reject(new Error('PLATFORM_SDK_TIMEOUT | Platform: iOS')),
            20000
        )
    )
]);
K — Knowledge

The timeout trap did not merely address the immediate symptom. It converted an invisible failure state into observable evidence. Unsampled timeout telemetry provided boundary proof for vendor escalation — transforming "ad impressions are down" into a reproducible, boundary-bounded signal the vendor could investigate and action.

  • Resolution: Third-party iOS SDK failed to settle promises under specific conditions → Vendor remediated; production fully restored.
  • Prevention: Unresolved async operations lacked hard cutoffs → Automated 24-hour sanity-check suite deployed to catch unresolved operations before they become incidents.

Operational Anti-Patterns

Incident anti-patterns share a common root cause: action is taken before the failure domain is established. Time pressure, incomplete tooling, and organizational dynamics all push teams toward intervention before evidence. H.A.C.K. makes these patterns explicit so they can be recognized — and interrupted.

1. Streetlight Anti-Pattern
"Searching where existing dashboards already look, rather than where the dark path lives."
Why it happens: Under pressure, engineers default to familiar tools. When time is short and stakes are high, the instinct is to search where answers have been found before — not where the evidence says the problem may actually be.
H.A.C.K. fix: Start with 5–10 minutes of surface checks. If no clear signal emerges, stop searching where the light already shines. Instrument the dark path instead. Count what entered the boundary versus what resolved, and let the unexplained gap identify where to look next.
2. Cross-Boundary Deflection Anti-Pattern
"Escalating across platform boundaries based on intuition rather than telemetry."
Why it happens: Cross-boundary failures are genuinely harder to prove. Without shared telemetry across both sides, assuming the problem lives somewhere else can feel reasonable. Suspicion is easier to voice than evidence is to gather.
H.A.C.K. fix: Isolate the failing journey before escalating. Measure what crossed the boundary, what returned, and what remained unaccounted for. Evidence transforms "your system is broken" into a reproducible, boundary-bounded signal the other side can investigate and action.
3. Random Change Anti-Pattern
"Tweaking configs or restarting nodes until symptoms clear, without establishing the cause."
Why it happens: Correlation feels like causation under incident pressure. When a change coincides with recovery, the brain naturally connects the two. Once the metric turns green, teams are often too relieved to question the explanation.
H.A.C.K. fix: Before declaring resolution, establish the mechanism. What changed in the execution path, and why should that change produce this recovery? If the explanation doesn't hold against the evidence, the symptom may be masked rather than resolved.
4. Traffic-Light Anti-Pattern
"Assuming the application is healthy because all infrastructure indicators report green."
Why it happens: Dashboards are optimized around signals we already know how to measure. Green infrastructure metrics create a false sense of completeness when the user journey itself isn't being measured.
H.A.C.K. fix: Treat infrastructure health as necessary, not sufficient. Pair component-level health with journey-level event accounting. If infrastructure is green but conversion is falling, follow the event path rather than the dashboard color.

Three Diagnostic Questions

At every boundary, Funnel Analysis reduces to the same three questions. If these cannot be answered from available telemetry, the first problem to solve is not the application code — it is the instrumentation gap.

Where?
Which boundary, runtime layer, dependency, or code path stopped accounting for events?
Which?
Which cohort isolates the anomaly — geography, OS, app version, network tier, or hardware?
When?
When was the funnel last balanced? That timestamp anchors the investigation.
Count what entered. Count what exited. Investigate the difference.

Pre-Incident Architecture Mapping

Observability gaps tend to emerge at architectural boundaries — services instrument their internals but leave transitions untracked. Layering Funnel Analysis onto the C4 Model provides a structured way to map diagnostic coverage before an outage occurs.

C4 LevelBoundary Focus & Diagnostic Objective
1 — Context Conversion and failure drop-offs across external boundaries: third-party vendor APIs, payment processors, social authentication flows, and cross-border gateways.
2 — Containers Transitions between runtime environments, microservices, and databases tracked with cross-boundary tracer strings (session_start → auth_ok → ad_req) and latency metrics (ΔT).
3 — Components Execution flows across application modules (AdLoadManager → SDK Adapter → Retry Handler). Narrows the failure domain to the specific component where event accounting breaks.
4 — Code Lowest-level async execution points: Promise.race() wrappers, explicit timeouts, fallback metrics, thread dumps, and targeted diagnostic hooks.

The goal is not to instrument everything. It is to ensure that critical application boundaries are observable before an incident makes them urgent.

C.H.A.I. — AI in the Loop

H.A.C.K. is effective without AI. LLMs can, however, accelerate specific points in the loop — not by acting as autonomous investigators, but by processing structured evidence and reducing the time between observation, hypothesis, and intervention.

C
Context & Candidate Probe
Given an architecture diagram or execution trace, an LLM can identify likely instrumentation gaps and propose diagnostic traps — candidate interventions for validation, not production changes to apply blindly.
H
Health Baseline Parsing
Given funnel metrics or log excerpts, an LLM can surface cohort-level patterns and identify divergence across dimensions that aggregate dashboards may hide.
A
Anomaly Hypothesis Isolation
Given trace dumps and deployment diffs, an LLM can organize and rank competing hypotheses by consistency with available evidence — reducing the hypothesis space before expensive diagnostic work begins.
I
Intelligence & Knowledge Synthesis
Given incident timelines and resolution artifacts, an LLM can synthesize findings into postmortems, regression-test scaffolding, and runbook updates — closing the loop into organizational knowledge.
AI can accelerate the loop. Evidence closes it.
The code solution is only one part of incident response. The real engineering asset is the knowledge that emerges: what failed, where it failed, how evidence exposed it, why the intervention worked, and how the system can automatically catch or prevent that failure class next time.

The H.A.C.K. Loop is not a checklist. It is a habit of thought — measure, investigate, validate, learn. Repeat.
