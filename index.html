The H.A.C.K. Loop

An Evidence-First Investigation Loop for Diagnosing Application Issues and Outages Through Event-Funnel Analysis, inspired by the USE Method and C4 Model.

Modern applications rarely operate in isolation. They depend on external modules, services, databases, infrastructure, and third-party APIs. During an incident, an engineer may not know every component, its implementation details, or even where the failure originated.

The problem H.A.C.K. addresses is not simply: "How do I find the error?"

It is: How do I understand the health of an application and trace an unexpected outcome back to the point where its expected behavior changed?

The Health Funnel

H.A.C.K. starts with a Health Funnel: a continuously maintained view of the application's expected event and data flow.

The funnel should be understandable at the C1 level and progressively drill down toward C4-level implementation details when investigation requires it. An engineer should be able to start with the application's expected flow — even without deep knowledge of a particular module — and progressively narrow the investigation.

The Health Funnel treats application event flow as a first-class observability signal.

Instead of looking only for explicit errors, it continuously asks:

  • Did the expected events happen?
  • In the expected order?
  • At the expected volume?
  • With the expected latency and dependencies?

This creates a baseline for the application's happy path and makes deviations visible.

Connecting USE to Application Events

The USE Method provides an established way to reason about resource health through:

Utilization → Saturation → Errors

H.A.C.K. applies an evidence-first investigation approach, inspired by the USE Method, to application event and journey health — a different analytical layer from infrastructure resource health.

For each important event or stage in the Health Funnel, we observe corresponding signals:

  • Utilization Is the expected application activity occurring?
  • Saturation Is work accumulating in buffers, queues, retries, or downstream dependencies?
  • Errors Are explicit failures occurring?

The important point is that not every application anomaly produces an explicit error. A missing event, unexpected drop-off, abnormal latency, queue growth, retry increase, configuration change, or third-party outage can all represent a deviation from the expected flow.

Therefore:

The Health Funnel establishes the baseline.
Anomalies are deviations from that baseline.
H.A.C.K. investigates those deviations and traces them toward their cause.

The Application as a Shared Investigation Map

The Health Funnel becomes a shared map of the application:

Expected Event Flow → Observed Event Flow → Anomaly → Investigation → Evidence → Knowledge

This map connects multiple levels of the system:

Application → Service → Module → Dependency → Event / Data Flow → Infrastructure

When an anomaly appears, the engineer does not need to immediately know which module is broken. They can start from the point where the expected flow diverged and progressively drill down. The cause may ultimately be:

  • an application defect
  • a recent code change
  • a configuration change
  • infrastructure degradation
  • dependency saturation
  • a third-party API failure
  • unexpected traffic or usage
  • data corruption or unexpected input
  • or another external condition

All of these become visible as evidence within the same investigation model.

Relationship to the USE Method

USE (Utilization, Saturation, Errors) is a resource-health framework. H.A.C.K. is a journey-health framework. They are complementary, not competing:

USE Method H.A.C.K. + Application Event Accounting
Layer Infrastructure resources Application journey
Primary question Is this component healthy? Did this event make it through?
Measures Utilization · Saturation · Errors Inputs · Outputs · ΔBuffer · Sinks · Unaccounted
Complementary concern Application journey and event-flow accounting are outside the primary scope of the USE resource-health model Resource saturation and component error rates — addressed by USE at the infrastructure layer

USE and Application Event Accounting answer different questions. A green resource-health dashboard does not by itself establish that an application journey is completing successfully. When resource health looks normal but operations are not reaching terminal states, follow the event flow.

USE Applied to Application Resources

The USE Method was designed for infrastructure resources, but its core discipline — define the resource, observe its utilization, saturation, and errors — applies equally to any clearly defined boundary. At the application level, a Matchmaking API, payment service, authentication flow, SDK boundary, queue, or internal module can be treated as the resource being observed. Applying this discipline at application boundaries is the author's adaptation, not a formal extension of the USE Method.

This means Health is not a fixed universal metric.

Health is a defined measure of whether a particular resource or application boundary is performing its intended function.

The key is to define what Utilization, Saturation, and Errors mean for that specific resource. For example, for a Matchmaking API:

Utilization How much of the required matchmaking work is actually being fulfilled? For example, required player matches successfully created relative to the total number of players requiring matches.
Saturation Is matchmaking work accumulating faster than it can be processed? For example, increasing queue depth, pending matchmaking requests, retries, or wait time.
Errors Which matchmaking requests reach an explicit failure state? For example, errors, timeouts, cancellations, or rejected requests.

Utilization is not a universal metric — it must be defined per resource:

CPU
Infrastructure resource
Utilization → CPU busy %
Matchmaking API
Application boundary
Utilization → Players matched / Players requiring matches
Payment Service
Application boundary
Utilization → Successful transactions / Payment attempts
Authentication Service
Application boundary
Utilization → Successful authentications / Attempts

The same principle applies to every boundary: define the resource, define what healthy utilization means, define what saturation looks like, define what constitutes an error, then observe using those signals.

This makes H — Health intentionally context-specific. The Health Funnel therefore does not prescribe one universal definition of health. It provides the structure for defining and observing health at every important application boundary.

Application Event Accounting

For a defined application boundary and a defined accounting window, every operation that enters should be attributable to a successful output, an explicit terminal sink, a bounded in-flight buffer awaiting resolution within its expected window, an intentional discard, or an unaccounted remainder. The remainder is the investigation signal.

INPUTS │ ┌────────────┼────────────────┐ ▼ ▼ ▼ SUCCESS EXPLICIT FAILURE BUFFER (Outputs) (Sinks: errors, (Bounded timeouts, cancels) in-flight) └────────────┴────────────────┘ │ Any remainder? │ ▼ UNACCOUNTED (no terminal state: silent hangs, drops) │ ▼ INVESTIGATE
$$\text{Inputs} = \text{Outputs} + \Delta\text{Buffer} + \text{Sinks} + \text{Unaccounted}$$
Inputs — Operations entering the defined boundary within the accounting window. Outputs — Successful completions reaching an expected terminal state. ΔBuffer — Legitimately bounded in-flight operations within their expected resolution window. Operations that exceed that window are reclassified as Unaccounted. Sinks — Explicit terminal outcomes: failures, errors, timeouts, cancellations, and intentional discards. Unaccounted — Operations with no attributable outcome within the accounting window. This is the investigation signal.

When Unaccounted is non-zero — when operations enter and no outcome can be attributed within the window — that remainder is not noise to discard. It is a signal.

An unexplained remainder is itself a signal.

A conventional failure takes a path. A catch block fires. A timeout resolves. An error counter increments. But an operation that never settles bypasses every one of those mechanisms — it neither succeeds nor fails. Infrastructure can remain completely idle and error-free while thousands of user operations are silently stuck. The system looks healthy because the component is healthy. The journey is not.

Application Event Accounting is complementary to distributed tracing. Distributed tracing follows individual requests or traces through system boundaries to identify where latency was introduced or where errors occurred. Application Event Accounting asks whether the population of operations entering a defined boundary can be accounted for as successfully completed, explicitly failed, bounded in-flight, intentionally discarded, or unexplained. Tracing explains individual paths; accounting exposes population-level gaps.

Infrastructure Health  ≠  Application Health  ≠  User Journey Health

Each layer can independently disagree. A component can be fully operational while the journey through it is failing. An aggregated metric can hide a cohort-specific collapse. An error counter can stay flat while events simply disappear.

Application Event Accounting explicitly measures a layer that resource-centric infrastructure monitoring does not necessarily capture.

Health Funnel Creation

A health funnel cannot be measured during an outage — it must be built before one. The Health Funnel is the author's observability construct: at each architectural boundary, three questions are applied. The C4 Model provides the architectural vocabulary for identifying where those boundaries are. The USE Method's resource-health discipline answers whether a boundary is resource-healthy. Application Event Accounting answers whether events are flowing through it correctly.

At every event flow boundary —
USE: Is this boundary resource-healthy?
Event Accounting: Are events flowing through it correctly?

The goal is not to instrument everything. It is to ensure that at every critical boundary, both the resource health (USE) and the event flow (Application Event Accounting) are observable before an incident makes them urgent.

Case Study: P0 Ad Funnel Collapse

100 ad requests entered the system.
  62 completed.
  38 were unaccounted for within the accounting window.

No error counter incremented. No alert fired. CPU was idle. Latency was nominal. Resource-level indicators remained nominal; the user journey was not.

The following investigation applies the H.A.C.K. Loop to a real revenue-critical incident. It illustrates concretely why component-level monitoring was insufficient, and how event accounting located the failure domain.

INC-2026-AD-REQ-DOWN  ·  P0 Revenue Critical  ·  iOS Ad Funnel Collapse

This is a reconstructed investigation. Technical details reflect the investigation's structure and findings. Incident identifiers and metrics are representative of the investigation, not publicly verifiable production records.

The Signal That Wasn't There

Gameplay engagement remained entirely normal. Infrastructure metrics stayed within nominal thresholds. No binary release had gone out. Yet interstitial ad impressions on iOS collapsed.

This is characteristic of a journey-level failure: component-level signals remain nominal while an application path stops completing. Without journey-level instrumentation, there is no starting point — only symptoms and guesses.

H — Health

The expected funnel was straightforward. In a healthy system, every successful ad_request should eventually produce either a success or failure at ad_load. Every initiated operation should reach a terminal state.

ad_request (success)  →  ad_load (success | fail)

The baseline expectation was near-complete resolution — effectively 100% of requests reaching a terminal outcome. Healthy cannot be defined during an outage. It must be established before one.

A — Anomaly

Discrepancy analysis between ad_request events and terminal ad_load resolutions exposed a large pool of unresolved operations:

REQUESTS (ad_request = success) ████████████████ 100% RESOLVED (ad_load success/fail) ██████████ 62% UNACCOUNTED (hanging promises) ██████ 38% ↑ Silent promise hangs
The problem was not an increase in explicit errors. It was missing terminal states.

38% of observed requests had no corresponding terminal event within the accounting window. The operations were initiated but never triggered a success or failure callback. Server and client CPU remained within nominal thresholds throughout.

The query below was not looking for errors. It was looking for requests that entered the system without reaching a terminal state — the accounting gap itself:

SELECT
    counter_date,
    event_category AS ad_type,
    COUNT(DISTINCT session_id) AS total_affected_sessions,
    SUM(CASE WHEN event_name = 'ad_request' AND event_status = 'success' THEN 1 ELSE 0 END) -
    SUM(CASE WHEN event_name = 'ad_load'   AND event_status IN ('success','fail') THEN 1 ELSE 0 END)
    AS net_hanging_promises
FROM telemetry.event_counts
WHERE app_id = 1000123 AND counter_date >= '2026-02-20'
GROUP BY counter_date, ad_type
HAVING net_hanging_promises > 0;

This query illustrates the accounting-gap concept. Production-grade accounting should correlate operations using a stable request or operation identifier and explicitly account for retries, duplicates, batching, and late-arriving events.

C — Candidate

Cohort isolation narrowed the anomaly to iOS, specific ad unit types, and a specific version range of a third-party social SDK. This produced a testable hypothesis: the SDK was failing to settle promises under certain iOS runtime conditions, with no callback firing on either the success or failure path — bypassing every standard error-handling mechanism.

A 20-second Promise.race() cutoff was injected at the interop boundary to validate that hypothesis. The intent was diagnostic: if operations were truly hanging indefinitely, the timeout would convert invisible hangs into explicit, observable rejections.

silent hang → bounded timeout → explicit failure → observable telemetry
const adLoadWithTimeout = Promise.race([
    sdk.loadAd(adUnitId),
    new Promise((_, reject) =>
        setTimeout(
            () => reject(new Error('PLATFORM_SDK_TIMEOUT | Platform: iOS')),
            20000
        )
    )
]);
K — Knowledge

The timeout trap did not merely address the immediate symptom. It converted an invisible failure state into observable evidence. Unsampled timeout telemetry provided boundary proof for vendor escalation — transforming "ad impressions are down" into a reproducible, boundary-bounded signal the vendor could investigate and action.

  • Resolution: Third-party iOS SDK failed to settle promises under specific conditions → Vendor remediated; production fully restored.
  • Prevention: Unresolved async operations lacked hard cutoffs → Automated 24-hour sanity-check suite deployed to catch unresolved operations before they become incidents.

Operational Anti-Patterns

Incident anti-patterns share a common root: action is taken before the failure domain is established. Time pressure, incomplete tooling, and organizational dynamics all push teams toward intervention before evidence. H.A.C.K. makes these patterns explicit so they can be recognized — and interrupted.

1. Traffic-Light Anti-Pattern
"Assuming the application is healthy because all infrastructure indicators report green."
Why it fails: Dashboards are optimized around signals already known to be measurable. Green infrastructure metrics create a false sense of completeness when the user journey itself isn't being measured — and a metric cannot signal what it isn't observing.
H.A.C.K. alternative: Treat infrastructure health as necessary, not sufficient. Pair component-level health with Application Event Accounting. If infrastructure is green but events are not resolving, follow the event path, not the dashboard color.
2. Streetlight Anti-Pattern
"Searching where existing dashboards already look, rather than where the failure actually lives."
Why it fails: Under pressure, engineers default to familiar tools. When time is short and stakes are high, the instinct is to search where answers have been found before — regardless of whether the evidence points there.
H.A.C.K. alternative: Start with 5–10 minutes of surface checks. If no clear signal emerges, stop searching where the light already shines. Instrument the dark path instead. Count what entered the boundary versus what resolved, and let the accounting gap identify where to look next.
3. Cross-Boundary Deflection Anti-Pattern
"Escalating across platform boundaries based on intuition rather than telemetry."
Why it fails: Cross-boundary failures are genuinely harder to prove. Without shared telemetry across both sides, assuming the problem lives elsewhere can feel reasonable — suspicion is easier to voice than evidence is to gather.
H.A.C.K. alternative: Isolate the failing journey before escalating. Measure what crossed the boundary, what returned, and what remained unaccounted for. Evidence transforms "your system is broken" into a reproducible, boundary-bounded signal the other side can investigate and action.
4. Random Change Anti-Pattern
"Tweaking configs or restarting nodes until symptoms clear, without establishing the cause."
Why it fails: Under incident pressure, correlation feels like causation. When a change coincides with recovery, the brain naturally connects the two. Once the metric turns green, teams are often too relieved to question the explanation — and the failure class goes uncaptured.
H.A.C.K. alternative: Before declaring resolution, establish the mechanism. What changed in the execution path, and why should that change produce this recovery? If the explanation doesn't hold against the evidence, the symptom may be masked rather than resolved.

Three Diagnostic Questions

At every investigation boundary, Application Event Accounting reduces to three questions. If these cannot be answered from available telemetry, the instrumentation gap is the first problem to solve.

Where?
Which boundary, runtime layer, dependency, or code path stopped accounting for events? In the case study, this was the interop boundary between the application and the third-party SDK — where operations entered but never returned.
Which?
Which cohort isolates the anomaly — geography, OS, app version, network tier, or hardware? In the case study, cohort isolation identified iOS, specific ad unit types, and a specific SDK version range — narrowing the investigation to a bounded, testable subset.
When?
When was the accounting last balanced? That timestamp anchors the investigation window. In the case study, the accounting gap began the day of a third-party SDK update — establishing a single deployment event as the investigation boundary.
Count what entered. Count what exited. Investigate the difference.

C.H.A.I. — AI in the Loop

H.A.C.K. does not require AI. The framework is grounded in telemetry, evidence, and explicit reasoning — not probabilistic inference. LLMs can, however, accelerate specific points in the loop by processing structured evidence and reducing the time between observation, hypothesis, and intervention. They act as investigation accelerators, not autonomous investigators. C.H.A.I. operates within the H.A.C.K. framework — it accelerates each step, but evidence and the engineer's judgment determine when a step is complete.

C
Context & Candidate Probe
Given an architecture diagram or execution trace, an LLM can identify likely instrumentation gaps and propose diagnostic traps — candidate interventions for validation, not production changes to apply blindly.
H
Health Baseline Parsing
Given funnel metrics or log excerpts, an LLM can surface cohort-level patterns and identify divergence across dimensions that aggregate dashboards may hide.
A
Anomaly Hypothesis Isolation
Given trace dumps and deployment diffs, an LLM can organize and rank competing hypotheses by consistency with available evidence — reducing the hypothesis space before expensive diagnostic work begins.
I
Intelligence & Knowledge Synthesis
Given incident timelines and resolution artifacts, an LLM can synthesize findings into postmortems, regression-test scaffolding, and runbook updates — closing the loop into organizational knowledge.
AI can accelerate the loop. Evidence closes it.

When infrastructure says everything is healthy but users say otherwise, stop looking only at resource health. Account for the application's events. Find what entered, what exited, what remains in flight — and then investigate what cannot yet be explained.

That unexplained remainder is where the investigation begins.

Health → Anomaly → Candidate → Knowledge.

The code solution is only one part of incident response. The real engineering asset is the knowledge that emerges: what failed, where it failed, how evidence exposed it, why the intervention worked, and how the system can automatically catch or prevent that failure class next time.

The H.A.C.K. Loop is not a checklist. It is a habit of thought — measure, investigate, validate, learn. Repeat.
